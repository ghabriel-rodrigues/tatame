# White-label runtime palette derivation

Type: grilling
Status: resolved
Blocked by: 01

## Question

How do we port the prototypes' `applyPalette()` — which derives the entire app palette from 3 academy colors `[deep, vibrant, accent]` via `color-mix(in oklab, ...)` — into the design system? Decide: runtime derivation (CSS `color-mix` on web is native; RN/Kotlin/Swift have no `color-mix` — need an oklab mixing implementation in TS/Kotlin/Swift or a shared derivation spec) vs build-time/server-side derivation (backend computes and serves the full derived scale per tenant, all clients just consume resolved colors); where the derivation algorithm lives so all 4 clients produce identical colors; how derived palettes interact with the semantic token layer and the ready-made palettes (default purple, navy/red, green/gold, black/gold); and how the runtime-only `--purple-ink`/`--pink-ink` tokens fit the derivation.

## Answer

*(answered as BOSS, per charter)*

**Decision: ONE canonical implementation — a pure-TS `derivePalette()` doing OKLab math, executing the shared `palette-recipe.json`. It is the single source of derived colors on web AND React Native; Kotlin and Swift carry line-for-line ports of the same math, pinned by shared golden fixtures. The web CSS `color-mix()` path from the prototypes is dropped for production (this supersedes ticket 01's "color-mix on web" note): identical hex output on all 4 platforms outweighs the zero-JS elegance, and the JS cost is one function run at boot.**

### 1. Recipe as data (per ticket 01)

`packages/design-system/tokens/palette-recipe.json` — the `applyPalette()` mix table (Aluno prototype, `applyPalette` at line 1007) transcribed verbatim as entries:

```json
{ "token": "purple-800", "base": "deep",    "pct": 72, "anchor": "#12061F" }
{ "token": "purple-300", "base": "vibrant", "pct": 46, "anchor": "W" }
{ "token": "purple-600", "base": "deep",    "pct": 50, "anchor": "vibrant" }
```

- `base` ∈ `deep | vibrant | accent`; `anchor` is a literal hex, another input slot, or symbolic `"W"` resolved per mode (`#FFFFFF` light, `#241E3A` dark — exactly the prototype's `W`).
- Ink tokens are mode-conditional entries: `purple-ink` = `deep` (light) / `mix(vibrant 65% #FFFFFF)` (dark); `pink-ink` = `mix(accent 64% #3B0A24)` (light) / `mix(accent 60% #FFFFFF)` (dark).
- Full coverage: purple-50…950, pink-50…700, purple-ink, pink-ink. Neutrals, semantics, glass are NOT in the recipe — they are static tokens (dark values via the `applyTema()` set, ticket 01/06).

### 2. Canonical executor

`packages/design-system/src/palette/derivePalette.ts`:

```ts
type BrandInput = { deep: string; vibrant: string; accent: string };
type Mode = 'light' | 'dark';
function derivePalette(input: BrandInput, mode: Mode): DerivedPalette; // Record<token, hex>
```

- Dependency-free: inline sRGB↔OKLab conversion + linear interpolation (~30 lines, Björn Ottosson's reference constants). culori rejected — not worth a dependency in the RN bundle for one mix function.
- Mix semantics = CSS `color-mix(in oklab, c1 p%, c2)`: convert both to OKLab, lerp at p, convert back, clamp to sRGB, emit uppercase hex. Tiny deltas vs. browser color-mix are irrelevant — the prototypes are reference, our TS output is canonical.
- Kotlin (`DerivePalette.kt`) and Swift (`DerivePalette.swift`) ports live in the design-system package next to the token pipeline; the recipe JSON is embedded into both at token-build time (codegen, nx `design-system:tokens` target) so recipes cannot drift.
- **Golden fixtures**: `tokens/palette-fixtures.json` — inputs = the 4 ready-made palettes (default purple `#4F2389/#8B3DEB/#EC5BAE`, navy/red `#14213D/#3A5FA8/#E63946`, green/gold `#1B4332/#2D6A4F/#E8A33D`, black/gold `#1F1F23/#4A4A52/#D4A017`) × both modes, outputs = expected hex maps generated by the TS executor. TS/RN tests and Kotlin/Swift unit tests all assert byte-equal hex against the same file. A port that drifts fails CI.

### 3. Web integration

- `applyBrand(derived: DerivedPalette)` writes the derived hex values onto the Lumira CSS custom properties (`--purple-700`, `--pink-ink`, …) at `document.documentElement` — plain hex, no `color-mix()` strings in production.
- The same `DerivedPalette` object feeds `createTatameTheme()` (ticket 02), so MUI vars and Lumira vars always agree.
- The ready-made palettes ship as presets: `TATAME_DEFAULT_BRAND` + `READY_MADE_PALETTES` (roxo default, navy/vermelho, verde/dourado, preto/dourado) — the admin identity screen offers them as one-tap options before custom picking.

### 4. Storage + tenant flow

- Academy branding = `{ deep, vibrant, accent, logoUrl }` on the academy (tenant) record; served in the tenant bootstrap/config payload (exact endpoint is the backend effort's call; the design system only defines the `BrandInput` contract).
- Clients cache the last branding locally (localStorage / AsyncStorage / DataStore / UserDefaults) for instant first paint; fallback = Tatame default purple. Convite flow inherits branding from the invite payload. Plataforma persona always renders default Tatame brand (SaaS owner surface is not white-labeled).
- Derivation is client-side at runtime, NOT server-side precomputation: payload stays 3 colors + logo (tiny, cacheable), server carries zero color code, and the admin identity screen gets instant live preview by calling `derivePalette` + `applyBrand` locally as the user picks colors. Server-side derivation rejected — it would duplicate the algorithm server-side or force clients to handle ~30 resolved colors per mode with no offline story.

### 5. Theming module API (design-system exports)

```ts
// platform-neutral entry
derivePalette(input: BrandInput, mode: Mode): DerivedPalette
TATAME_DEFAULT_BRAND: BrandInput
READY_MADE_PALETTES: Record<'roxo'|'navy'|'verde'|'preto', BrandInput>
// web entry
applyBrand(derived: DerivedPalette): void            // writes Lumira CSS vars
createTatameTheme(derived: DerivedPalette, mode): Theme  // ticket 02
// RN entry
createTatameTokens(derived: DerivedPalette, mode): TokenSet // static tokens overlaid with derived scale
```

Semantic-layer interaction: derivation only rewrites the raw brand scales (+inks); semantic tokens (`fg-*`, `brand-*`, `bg-*`) keep pointing at those scales, so the whole app re-brands transitively — same behavior as the prototypes.

### 6. Ticket 06 implications (dark theme)

`derivePalette` already takes `mode` and encodes the dark anchors (`W = #241E3A`) and dark ink mixes. Order of operations is fixed here: **static dark token set first (the `applyTema()` neutral/glass/semantic remix, already in `tokens.json` per ticket 01), then `derivePalette(brand, 'dark')` overlays the brand scales.** Ticket 06 therefore only needs to decide per-platform propagation (MUI colorSchemes toggle, RN context, Compose/SwiftUI dark variants) and persona rollout — the color math is closed.
