# 001 — Authentication & Authorization (Phase 1)

Status: ready-for-agent
Personas covered: Aluno, Professor, Admin da academia, Responsável, Plataforma (Owner/Suporte/Financeiro), Convite (public flow)

## Problem Statement

Nobody can use Tatame yet. Every persona surface in the design handoff — the five apps plus the public invite flow — begins at a login screen, and every business rule downstream (multi-tenant isolation, RBAC, professor-has-no-financial-access, suspension blocking, delinquency read-only, guardian-only-own-dependents, audited "entrar como admin") depends on knowing who the user is, which academy they are acting in, and in which role. Until authentication and authorization exist end to end — database, backend, web, and the three mobile apps — no other feature can be built without faking identity, and any faked identity would bake tenant-isolation bugs into the foundation of a multi-tenant SaaS.

There is also no self-signup in the product: students and guardians only enter through invite links generated by a professor or admin, with academy, class, and plan inherited from the link, and minors always bound to a guardian. Without the invite acceptance flow, an academy cannot onboard a single student.

## Solution

A single identity system shared by all clients: users log in with email and password and receive a short-lived access token plus a rotating refresh token. One account can hold many memberships (the same person can be a professor in academy A and an admin in academy B, or a platform staff member); the active membership is baked into the token, and switching academy or persona re-issues tokens without re-login. Authorization is enforced server-side by a layered guard chain (authentication → academy status → role → permission toggles), with Postgres row-level security as the tenant-isolation backstop. Platform staff can enter any academy as its admin through an audited, time-boxed impersonation session, visibly flagged in the client. Password reset works by single-use emailed token; signup exists only through the public invite flow, which atomically creates the user, membership, and student/guardian records and ends with the user logged in. Logout revokes the server-side session everywhere.

Each client stores the session in its platform-appropriate secure fashion (httpOnly cookie on web; secure storage on the three mobile apps; access token in memory everywhere), restores it silently on startup, and lands the user in the shell matching their active role — including the "download the app" landing for mobile-only personas on web and the "use the web console" screen for web-only personas on mobile.

## User Stories

### Login & session (all personas)

1. As any user (aluno, professor, admin, responsável, or platform staff), I want to log in with my email and password, so that I can access my persona's surface.
2. As any user, I want a failed login to tell me the credentials are invalid without revealing whether the email exists, so that my account is not enumerable.
3. As any user, I want my session to survive app/browser restarts without re-entering my password, so that daily use is frictionless.
4. As any user, I want my session restored silently while the splash/loading screen shows, so that I land directly in my home shell instead of the login screen.
5. As any user, I want in-flight requests to transparently recover when my access token expires, so that I never see spurious "session expired" errors mid-use.
6. As any user, I want to be sent back to the login screen with a clear message when my session is truly revoked or expired, so that I understand why I was signed out.
7. As a mobile user who opens the app offline with a stored session, I want to enter the app shell in a degraded/stale state instead of being bounced to login, so that connectivity blips do not lock me out.
8. As any user, I want my login stub screens for "Esqueci minha senha" and the invite notice rendered exactly as designed in the handoff, so that the product looks finished from the first screen.

### Multi-membership & switching

9. As a user with multiple memberships (e.g. professor in academy A and admin in academy B), I want to log in once and see all my academies/personas, so that I can pick where to act.
10. As a multi-membership user, I want to switch my active academy or persona without re-entering my password, so that moving between contexts is instant.
11. As a multi-membership user, I want my most recently used membership chosen automatically at login, so that I usually land where I meant to go.
12. As a user, I want my active role and academy to be exactly one at a time (never a union of my roles), so that what I can do is always unambiguous.
13. As a platform staff member who also holds an academy admin membership, I want the web app to default me to the platform console, so that I reach academies through the governed (audited) impersonation path.

### Aluno

14. As an aluno, I want to log in on mobile and land on the aluno home shell, so that I can check in, see my agenda, and track my graduation.
15. As an aluno, I want to see only my own data (my attendance, my graduation, my charges), so that other students' information is never exposed to me.
16. As an aluno who tries the web app, I want a friendly "download the app" landing instead of an error, so that valid credentials never feel broken.

### Professor

17. As a professor, I want to log in and land on the professor dashboard shell, so that I can run roll calls and manage my classes.
18. As a professor, I want no financial surface to exist for my role — not hidden, structurally absent — so that academy finances are never one bug away from me.
19. As a professor, I want to generate invite links (aluno or responsável variant) bound to my academy and a class, so that onboarding students is a link share, not data entry.
20. As a professor whose academy admin disabled one of my toggleable permissions (e.g. creating events), I want the action rejected server-side and hidden client-side, so that the admin's configuration is actually enforced.

### Admin da academia

21. As an academy admin, I want to log in on web and land on the admin console shell, so that I can manage my academy.
22. As an academy admin, I want to manage per-role permission toggles for my academy, so that I control what professors, alunos, and responsáveis can do.
23. As an academy admin, I want hard rules (like professor financial access) to be impossible to enable via toggles, so that misconfiguration cannot break charter guarantees.
24. As an academy admin, I want to generate invite links with academy, class, and plan inherited, so that new members arrive pre-bound to the right context.

### Responsável

25. As a responsável, I want to log in on mobile and land on the dependents panel, so that I can follow my children's training and payments.
26. As a responsável, I want access strictly limited to my own dependents — a foreign child's id behaving as if it does not exist — so that other families' data is never leaked, not even its existence.

### Plataforma (Owner / Suporte / Financeiro)

27. As a platform staff member, I want to log in on the same login endpoint as everyone else and land on the platform console, so that there is one identity system to secure.
28. As a platform owner or support member, I want to "entrar como admin" of any academy, so that I can support customers seeing exactly what their admin sees.
29. As a platform finance member, I want to be unable to impersonate academies, so that financial staff cannot act inside customer tenants.
30. As a platform staff member, I want optional TOTP two-factor on my account, so that the accounts with the most reach are hardest to steal.
31. As a platform staff member with TOTP enabled, I want login to require my one-time code, so that my password alone is not enough.

### Impersonation behaviors

32. As an impersonating support user, I want my impersonated session marked in the token and capped at one hour, so that the elevated context cannot linger.
33. As an impersonating support user, I want a persistent, non-dismissable banner ("você está como admin de X") with an exit action, so that I always know which hat I am wearing.
34. As a platform owner, I want every impersonation start and every mutating action performed under impersonation audited (who, which academy, what, when), so that support access is accountable.
35. As an impersonating user, I want to see exactly what the academy admin sees and nothing more (tenant-scoped like any admin), so that impersonation grants no super-powers.
36. As an impersonating user, I want sensitive account actions (switching membership, changing passwords, managing TOTP, chaining another impersonation) blocked in the impersonated session, so that impersonation cannot escalate.
37. As an impersonating user, I want ending impersonation to return me to my untouched platform session, so that exiting is safe and instant.

### Academy status: suspension & delinquency

38. As a platform owner, I want a suspended academy's members blocked from everything except seeing the blocking screen and logging out, so that suspension actually suspends.
39. As a member of a delinquent academy, I want read access to keep working while mutations are rejected, so that delinquency degrades service without destroying it.
40. As an aluno or responsável in a delinquent academy, I want the payment endpoints to keep accepting my payment, so that the academy can settle the debt that caused read-only mode.
41. As a platform owner, I want reactivating an academy to restore access instantly without forcing everyone to re-login, so that recovery is as fast as suspension.

### Password reset

42. As any user, I want to request a password reset by email and always get the same acknowledgment, so that I can recover access without leaking which emails have accounts.
43. As any user, I want the reset email to contain a single-use, short-lived link that deep-links into the app with a web fallback, so that reset works from any client.
44. As any user, I want completing a reset to revoke all my sessions everywhere and require a fresh login, so that whoever had my old password (or intercepted the email link) is signed out.

### Convite (public invite flow)

45. As an invited person opening an invite link, I want a landing page showing the academy (with its branding), class, and plan I am joining, so that I know what I am accepting before entering data.
46. As an invited person, I want an expired, revoked, or used-up link to show a clear error state, so that dead links fail honestly.
47. As an invited aluno (adult), I want a stepped signup that creates my account already bound to academy, class, and plan, so that onboarding is complete in one pass.
48. As an invited responsável, I want to register myself and my children in the same stepped flow, so that my minor dependents are enrolled with me as their guardian from the start.
49. As a minor, I want the system to refuse to create me a standalone aluno account via an aluno invite, so that the "minor always linked to a guardian" rule cannot be bypassed at signup.
50. As an invited person completing signup, I want to end up logged in (mobile: in the app shell; web: on the branded "download the app" landing), so that success flows straight into using the product.

### Logout

51. As any user, I want "sair" to revoke my current session server-side and return me to the login screen, so that logging out on a shared device is real, not cosmetic.
52. As any user, I want logout to complete locally even if the network call fails, so that I am never trapped in a session I tried to end.
53. As any user, I want a "log out of all devices" capability (also triggered by password reset), so that I can respond to a lost or stolen device.
54. As any user, I want all cached data cleared from the client at logout and at any tenant switch, so that no data bleeds across users or academies on the same device.

## Implementation Decisions

### Credentials & token model

- Email + password only in v1. Password hashing: argon2id with OWASP-recommended parameters. A password-changed timestamp on the user invalidates access tokens issued before a password change.
- Access token: JWT, HS256, 15-minute TTL, held in memory only on all four clients. Minimal claims: subject (user), session id, membership id, tenant id (null for platform), active role, optional impersonation flag plus actor claim (RFC 8693 style). Never in the payload: email, password hash, or permission toggles (toggles come from the bootstrap endpoint so changes apply without re-issue).
- Refresh token: opaque 256-bit random, 30-day absolute cap fixed at login, rotating on every refresh, stored server-side as a SHA-256 hash. A session is the token family: presenting an already-used refresh token is a theft signal that revokes the whole session. Reuse detection is mandatory, not optional.
- Refresh transport is client-selected at login (`cookie` or `body`) so one endpoint set serves all clients: web receives it as an httpOnly, Secure, SameSite=Strict cookie path-scoped to the auth endpoints (first-party because web and API share an origin via proxy; bearer-header APIs are otherwise CSRF-immune); mobile clients receive it in the response body and store it in platform secure storage.

### One account, N memberships

- One global user row per person; personas come from memberships: academy memberships (role: student/aluno, professor, admin, guardian/responsável — per tenant) and platform memberships (role: owner, support, finance; tenant null). The same person may hold many.
- Login binds tokens to one active membership (single → it; else last-used; else first) and returns the full membership list for the client switcher. Switching membership re-issues the token pair on the same session with new tenant/role claims — no re-login. A request carries exactly one active role; guards never union roles across memberships.
- The bootstrap endpoint returns user profile, all memberships, active membership, academy status, and the resolved permission-toggle map — clients render from it and never decode the JWT themselves.

### Authorization: layered global guard chain, default deny

1. JWT auth guard verifies the bearer token (public-route decorator bypass for login/refresh/reset/invite and webhook endpoints) and populates the request-scoped context (user, session, membership, tenant, role, impersonator) in async-local storage — the single source the tenant-scoped database wrapper reads.
2. Academy status guard (skipped for platform tokens): Ativa/Trial pass; Inadimplente allows reads but rejects mutations (stable error code) except routes explicitly marked as read-only-bypass (paying the overdue bill must stay possible); Suspensa rejects everything except the bootstrap and logout endpoints so clients can render the blocking screen and sign out. Status changes never revoke sessions; reactivation is instant. Status is resolved via a short-TTL in-process cache.
3. Roles guard with default deny: any non-public route without explicit role metadata is a 403; persona-scoped controllers bind role to surface at class level; routes open to any authenticated user are explicitly marked so.
4. Permissions guard on the toggleable subset only: per-academy, per-role toggle rows (absent row = code default); denial has its own stable error code. Hard rules are structural (the billing surface simply has no professor controller), and ownership rules (guardian-only-own-dependents, aluno-only-own-data) are service-level filters on the caller's identity inside the tenant transaction — a foreign id is a 404, never a 403, so existence does not leak.

### Tenant isolation & RLS integration

- Postgres row-level security is the isolation backstop: tenant-scoped tables carry forced RLS keyed on a per-transaction tenant setting derived from the verified token; an unset tenant context fails closed. Composite tenant-leading foreign keys prevent cross-tenant references at the constraint level.
- Auth-global tables (users, credentials, sessions, refresh tokens, password reset tokens) have forced RLS with self-access policies; pre-auth operations (login by email, refresh rotation, password reset, invite landing/accept) go through a small set of security-definer functions owned by the migrations role — RLS stays forced and the only bypass is a narrow, audited signature used exclusively by the identity module.
- The Phase-1 schema is exactly the auth-critical set: users, credentials, sessions, refresh tokens, password reset tokens, memberships, role permissions (toggles), invites, academies, platform users, platform plans, academy subscriptions. Everything else lands with its own feature slice.

### Impersonation ("entrar como admin")

- Minted from the platform surface (owner and support only; finance excluded) in one unit of work: write the audit record, create a new session flagged with the impersonator and a 1-hour absolute cap, return a token pair claiming the target tenant with admin role, impersonation flag, and actor claim. The impersonated session runs on the regular tenant-scoped pool — support sees exactly what the admin sees.
- A global interceptor audits every mutating request while an impersonator is present in context. Impersonated tokens are rejected on membership switch, password, TOTP, and impersonation endpoints (no chaining). Ending impersonation is a logout of the impersonated session; the platform session is untouched. Clients render the persistent banner from the impersonation fact in the bootstrap payload.

### Password reset & platform 2FA

- Forgot: always 202 (no enumeration); if the user exists, a single-use 1-hour token (hash stored) is emailed via the transactional-email module with deep link plus web fallback. Reset: verifies token, sets the new argon2id hash, stamps password-changed, consumes the token, and revokes all the user's sessions. No auto-login after reset.
- Platform users get opt-in TOTP: setup/enable endpoints, encrypted secret at rest, hashed single-use recovery codes; login for a TOTP-enabled user returns a short-lived challenge completed by a dedicated endpoint. Enforcement flag exists but is off in v1.

### Invite acceptance — the only signup

- Invite tokens: 256-bit random, hash stored, 7-day validity, optional max uses, revocable; payload binds academy, class, plan, and kind (aluno vs responsável); created by professor or admin.
- Public landing endpoint validates the token and returns academy branding, class, plan, and kind. Acceptance is one database transaction: create user with credentials, create membership, create the student (aluno kind) or the guardian plus N dependent students (responsável kind), consume the invite, and emit the domain event enrollment listens to. The minor rule is enforced here: an aluno invite for a minor is rejected with a stable error code — minors enter only via the responsável variant. The response is a full token pair: signup ends logged in.

### Session storage & bootstrap per client

- Web: access token in a memory-only singleton auth store; refresh cookie as above; boot runs one silent refresh before any guarded route renders (states booting → authed/anon); the fetch layer does single-flight 401 refresh with request replay; auth loss clears the query cache and redirects to login. Route guards are UX only (server RBAC is the enforcement) and follow the post-login redirect rule, including the "download the app" landing for mobile-only personas. Query cache is cleared on every login, logout, and impersonation boundary.
- React Native: refresh token in secure storage (device-only accessibility, no cloud migration), access token in memory; one binary hosting all three mobile personas with the shell switched on the session role; admin/platform roles get a "use the web console" screen; cold start silently refreshes behind the splash; offline start with a stored token enters a stale shell rather than login.
- Android (Kotlin): networking depends only on a token-store interface; refresh token encrypted at rest under a hardware-keystore key, access token in a memory-only provider; single-flight refresh via the HTTP client's authenticator; suspension/read-only error codes surface as session state, not per-call failures.
- iOS (Swift): refresh token in the Keychain (when-unlocked, this-device-only), access token in memory inside the refresh-coordinator actor; auth middleware injects the bearer header and performs retry-once refresh with single-flight semantics; one typed API error surfaces tenant-state codes to the session layer.
- All four clients implement the same contract: bearer header, 401 single-flight refresh with one replay, hard logout on refresh failure, full cache clear on logout and tenant switch.

### Endpoint list (API contract, identity surface, versioned prefix)

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /auth/login` | public | credentials → token pair (or TOTP challenge) + memberships |
| `POST /auth/login/totp` | challenge token | complete platform 2FA login |
| `POST /auth/refresh` | refresh token (cookie/body) | rotate pair, reuse detection |
| `POST /auth/switch` | bearer | re-issue tokens for another membership |
| `POST /auth/logout` | bearer | revoke current session |
| `POST /auth/logout-all` | bearer | revoke all sessions |
| `GET /auth/me` | bearer | user + memberships + active context + toggles |
| `POST /auth/password/forgot` | public | send reset email (202 always) |
| `POST /auth/password/reset` | public | consume token, set password, revoke sessions |
| `POST /auth/totp/setup`, `POST /auth/totp/enable` | bearer (platform) | opt-in 2FA |
| `GET /public/invites/:token` | public | invite landing payload |
| `POST /public/invites/:token/accept` | public | atomic signup, returns token pair |
| `GET /admin/permissions`, `PUT /admin/permissions` | bearer (admin) | manage permission toggles |
| `POST /platform/academies/:id/impersonate` | bearer (owner, support) | audited impersonation session |

Stable problem+json error codes (shared registry): invalid credentials, token expired, refresh reused, MFA required/invalid, invite invalid-or-expired, minor-requires-guardian, reset invalid-or-expired, forbidden role, permission disabled, impersonation restricted, tenant suspended, tenant read-only.

## Testing Decisions

- A good test exercises external behavior through the API (or the client's public seam), never implementation details: assertions are on status codes, stable error codes, and observable state — not on guard internals, hash formats, or storage layouts.
- Backend e2e suite (the primary seam, against a real Postgres with RLS active) must cover: RBAC matrix — professor hitting any admin or billing route → 403; switch to a membership you don't own → 403; toggle off → permission-disabled code; refresh-token reuse → whole family revoked and next refresh fails; expired/used invite → error; minor aluno invite → minor-requires-guardian; reset token single-use and all sessions revoked after reset; suspended academy → everything 403 except bootstrap and logout; read-only academy blocks mutations but not bypass-marked payment routes; guardian fetching a foreign dependent → 404; impersonated mutation writes an audit row; impersonated token on switch/password/TOTP/impersonate endpoints → restricted code.
- Two meta-tests keep the system honest as it grows: the route-metadata test reflects over all registered routes and asserts every handler is public or carries an explicit role stance (plus: no professor route served by the billing module); the RLS meta-test asserts tenant tables fail closed with an unset tenant context.
- Web: component/integration tests for the auth store state machine (booting → authed/anon), single-flight 401 refresh with replay, guard redirects (including the download-the-app landing), and cache clearing at logout/impersonation boundaries — mocking the HTTP layer, not the store.
- Mobile: the refresh single-flight logic and error mapping are pure-logic tests on each platform (mock server / mock transport / fake token store); cold-start restoration and role-gated shell selection get one integration test per client.
- Prior art: this is the first feature, so this suite is the prior art — its patterns (e2e-first, stable-code assertions, meta-tests, per-client seam fakes) set the template later specs reference.

## Out of Scope

- 2FA for academy users (aluno/professor/admin/responsável) — no design surface; the platform TOTP challenge shape is the extension point.
- Biometric gating of stored sessions (Face ID / fingerprint unlock) — storage call sites isolate the option so it can be enabled later.
- OAuth/social login — the credentials provider enum leaves room; nothing built.
- Web surfaces for aluno, professor, and responsável — web serves admin and plataforma only; mobile-only personas get the "download the app" landing.
- Geolocation-verified check-in (and check-in generally) — later feature slices.
- Rate limiting and abuse controls on auth endpoints — designed separately (dedicated ticket), not part of this slice's acceptance.
- Mandatory TOTP enforcement for platform owners — flag exists, off in v1.
- "Impersonation started" notification to the academy owner — product decision deferred.

## Further Notes

- Suspension and delinquency are authorization concerns, not authentication: sessions survive status changes by design so reactivation is instant.
- The worst-case validity of a stolen access token is its 15-minute TTL (no denylist in v1); revocation-sensitive contexts (impersonation) compensate with a 1-hour session cap.
- Login screens across all six surfaces are already designed in the handoff (splash, login, "Esqueci minha senha" stub, invite notice; convite landing/steps/success) and must be recreated pixel-perfect with Lumira tokens through the theme engine — no hardcoded colors.
- Client role names in PT-BR (aluno, responsável) are UI copy; the schema and shared enums use English role names.
- Delivery follows the fixed order DB → backend → web → mobiles; the checklist below is mirrored into the root README, and checking a box there is the only "ticket closing" this project has.
